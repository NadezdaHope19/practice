# Кратко описание логики БД
## Регистрация пользователя
### users
Таблица users хранит пользователей платформы.  
Связь с таблицей privacy_policies: храним информацию о том, какая версия офферты и согласия на обработку данных была подписана при регистрации.  
Важное ограничение: phone должен быть уникальным, один аккаунт на один номер телефона.  
| Имя поля | Тип  | Ключ | Условия, ограничения | Назначение |
|:--------:|:----:|:----:|:--------------------:|:----------:|
| user_id  | uuid | PK | not null, unique | первичный ключ |
| privacy_id | integer | FK | not null | связь с таблицей privacy_policies |
| user_name | varchar(200) | | not null | имя пользователя |
| phone_number | varchar(15) | | not null, unique | телефон, на который зарегистрирован аккаунт |
| registred_at | timestamptz | | | дата регистрации аккаунта |
| is_blogger | boolean | | | роль "блогер" |
| is_seller | boolean | | | роль "селлер" |
| status_user | enum | | | статус аккаунта |
| rating_avg | numeric(3, 2) | | | средний рейтинг |
| rating_count | integer | | | количество оценок пользователя |
| blocked_at | timestamptz | | | дата блокировки пользователя |
### privacy_policies
Таблица privacy_policies хранит офферты и согласия об обработке данных, которые действовали на момент регистрации.  
Связь с таблицей users: одну офферту могут подписать несколько пользователей.  
Важное ограничение: created_at по умолчанию текущее время и дата при создании записи, is_active=true не больше одной записи в таблице.  
| Имя поля | Тип  | Ключ | Условия, ограничения | Назначение |
|:--------:|:----:|:----:|:--------------------:|:----------:|
| privacy_id | integer | PK | not null, unique | первичный ключ |
| version | varchar(20) | | not null, unique | номер версии офферты |
| offer_text | text | | not null | текст офферты |
| consent_text | text | | not null | текст согласия |
| created_at | timestamptz | | not null | дата публикации офферты |
| is_active | boolean | | default true, limit 1 | актуальность документов |

## Селлер создает рекламмную кампанию
### campaigns
Таблица campaigns хранит все рекламмные кампании (РК), которые создают селлеры.  
Связь: 
- с users: одна кампания, один user_id, но у одного user_id может быть несколько кампаний;
- с topics: одна кампания, один topic_id.

Важное ограничение: удаление кампании "мягкое", budget максимальное значение 500000 руб.  
| Имя поля | Тип  | Ключ | Условия, ограничения | Назначение |
|:--------:|:----:|:----:|:--------------------:|:----------:|
| campaign_id  | uuid | PK | not null, unique | первичный ключ |
| seller_id | uuid | FK | not null | создатель РК, связь с users |
| topic_id | integer | FK | not null | тема РК, связь с topics |
| description | text | | not null | описание РК |
| budget | numeric(8, 2) | | not null, max 500000 руб  | бюджет РК |
| settings | JSONB | | | гибкие настройки РК |
| payment_type | varchar(20) | | not null | тип оплаты |
| status_campaign | enum | | not null | текущий статус кампании |
| created_at | timestamptz | | not null | дата создания кампании |
| deleted_at | timestamptz | | | дата удаления кампании |

## Блогер заполняет профиль
### user_platforms
Таблица user_platforms хранит все добавленные платформы блогерами.  
Связь:
- со справочниками audience и reach: у одной платформы может быть один диапазон из справочника.
- с таблицей topics: у одной платформы может быть несколько тематик (связь через промежуточную таблицу topic_user_platform).

Важное ограничение: у одного user_id может быть несколько разных платформ, у одного platform_id не может быть добавлено больше 10 тематик блога, удаление записей "мягкое", не может быть удалена единственная верифицированная запись.  
| Имя поля | Тип  | Ключ | Условия, ограничения | Назначение |
|:--------:|:----:|:----:|:--------------------:|:----------:|
| platform_id  | uuid | PK | not null, unique | первичный ключ |
| blogger_id | uuid | FK | not null | блоггер, владелец соцсети, связь с users |
| audience_id | integer | FK | not null | связь со справочником кол-ва аудитории audience |
| reach_id | integer | FK | not null | связь со справочником кол-ва охвата reach |
| platform | enum | | not null  | платформа: "Instagram", "Telegram", "TikTok", "YouTube", "VKontakte", "Dzen"
| social_link | varchar() | | not null | ссылка на аккаунт |
| region | enum | | not null | регион: "Россия", "мир", "Казахстан" |
| status | enum | | not null | статус записи |
| created_at | timestamptz | | not null | дата добавления платформы |
| deleted_at | timestamptz | | | дата удаления платформы |

### topics
Таблица topics хранит тематики используемые при заполнении своих соцсетей.  
Связь: 
- c таблицей user_platform: у одной соцсети может быть несколько тематик, cвязь многие ко многим организуем через промежуточную таблицу topic_user_platform;
- c таблицей campaigns: один к одному.

| Имя поля | Тип  | Ключ | Условия, ограничения | Назначение |
|:--------:|:----:|:----:|:--------------------:|:----------:|
| topic_id | integer | PK | not null, unique | первичный ключ |
| topic_name | varchar(50) | | not null, unique | наименование тематики |

## Система отправляет оффер блогеру
### offers
Принято решение хранить офферы отдельно от сделок, чтобы не перегружать таблицу сделок, которая крайне важна и историю хранить нужно достаточно длительно, а отклоненные офферы можно чистить с периодичностью.

### deals
Один оффер - одна сделка, связь один к одному по id_оффера, поле is_safe_deal для безопасных сделок, поля campaign_id и blogger_id дублируем для удобства отображения актуальных сделок, чтобы не использовать сложные запросы

## Safe-сделка и платеж
### safe_deal_payments
Безопасная сделка - поле is_safe_deal в таблице deals. Связь с таблице deals один ко многим, потому что предусмотрена повторная оплата, в случае неудачи. Храним количество попыток оплаты, код ошибки от системы и текст ошибки. Внешний payment_id для идентификации платежа, должен быть уникальным, чтобы не списать оплату дважды. Payment_method - все системы предусмотренные для оплаты (enum).

## Подписка блогера
### subscriptions
Подписки пользователя. Связь пользователя с подписками один ко многим, потому что может быть несколько подписок. Храним дату оформления подписки, когда стартует, когда заканчивается, по какому тарифу была оформлена, какая применена скидка, сколько финальная стоимость.

### subscription_templates
Шаблон тарифа. Храним дату создания, актуальность, базовую стоимость, на какой период действует. Один тариф может быть во многих подписках, связь один ко многим

## Промокоды
### promos
Условия промокода хранима гибкой структурой - rules_json, списки тарифов на которые распространяется - массив идентификаторов template_ids. Один промокод может быть применен в нескольких подписках

## Файлы
### files
Файлы принадлежат конкретному пользователю (один ко многим). Один и тот же файл моет быть использован в нескольких кампаниях (многие ко многим), связь организуем через таблицу files_campaign. ссылку на файл храним в storage_path.

## Отзывы
### reviews
Связь со сделкой - один ко многим, отзыв может оставить как селлер, так и блогер. Нужно ограничить, что каждая сторона может оставить не более одного отзыва (составной ключ deals_id,user_id). Храним оценку rating, пересчитываем rating_avg и rating_count в таблице users один раз в сутки процедурой или реализуем триггер в момент вставки (?).

## Сообщения и уведомления
Сообщения и уведомления разделены, чаты необходимо хранить длительно, после завершения сделки, они жестко связаны с таблицей deals.
### notifications
В таблице поля entity_name и entity_id чтобы из уведомления по сделке или офферу можно было сразу перейти на нужную страницу

### messages
Таблицу привязываем к deals через промежуточную таблицу chats, в случае разбора спора и необходимости подключения третьей стороны, потребуется создать еще чаты с продавцом и блогером, которые должны быть привязаны к сделке. В message храним автора сообщения, дату создания и идентификатор прочтения.
